# AetherFire Anti-Drift - Interface Economy and State Stabilization v1.1

> Type: local anti-drift config for task-scoped economic and institutional interfaces.
> Not: a CI, world bible, complete economy model, fiscal law, banking design, or new canon.
> Scope hook: Section 1/3 tasks involving Civil, Undie, Forum, Facilities, Dorm, Rule Zone, Yellow, gambling, entertainment, logistics, labor, housing, trade, state intervention, or related economy-institution interfaces.
> Authority hook: inherits source authority and priority from the active AetherFire CI and active AetherFire Source Router. Historical chat anti-drift routers are not authority sources. This file does not create canon, override confirmed canon, or turn proposals into facts.
> Core purpose: allow enough depth to close the current task's causal path while preventing interface questions from expanding into full economic realism.

---

# 1. Scope Clamp

This file controls task-local analysis.

It does not authorize full-domain economic modeling unless the user explicitly asks for a full-economy audit, macro model, or system-wide economic design.

Open only the mechanism that can change the current task's conclusion, feasibility, authority path, failure path, exploit path, or canon-status label.

Potential relevance to the wider economy is not enough.

```text
TASK-LOCAL CLOSURE > DOMAIN COMPLETENESS
CAUSAL CLOSURE != ACCOUNTING CLOSURE
INTERFACE DEPTH != FULL ECONOMY MODEL
BLACK BOX != FLATTENED ONTOLOGY
UNKNOWN != PERMISSION TO INVENT
```

# 2. Core Invariants

Depth is allowed only when it serves at least one task-relevant factor:

- function;
- actor and authority;
- input/output data;
- dependency or constraint;
- incentive or access;
- interface with another node;
- failure and fallback;
- cross-node consequence;
- exploit or adaptation path.

Do not open deeper mechanisms because:

- the question is interesting;
- real economies usually contain that layer;
- more detail would feel realistic;
- the model wants a complete diagram;
- an unknown could be filled;
- a subsystem could be modeled more deeply;
- a source contains adjacent detail;
- no number exists yet.

# 3. Open Rule

MUST_OPEN applies only when the hidden layer can change the answer to the current task.

Open the next layer if at least one condition is true:

1. the user explicitly asks for it;
2. the mechanism itself is the canon point being clarified;
3. two possible mechanisms lead to different task conclusions;
4. authority, feasibility, permission, or veto power depends on it;
5. an exploit or failure path crosses the black box;
6. a transition or proposed action cannot be evaluated without it;
7. abstraction would hide information flow, authority, resource access, capacity, enforcement, or veto power that matters now;
8. intervention could conflict with canon, break an invariant, create a relevant consequence, or be blocked by geopolitics;
9. simultaneous failures may exceed capacity in the current scenario;
10. the fallback receiver may reject, overload, or create a handoff loop.

Continue with conditional branches when possible. Ask the user only when missing data would materially change the result and useful bounded branches are not possible.

---

# 4. Stop Rule

MAY_STOP when all task-relevant conditions at the current interface are resolved at the required resolution:

- function and input/output;
- actor, authority, and information path;
- dependency, constraint, and incentive;
- transmissible interface;
- fallback receiver and valid intake path, if failure is relevant;
- known material conflicts or dependency loops at this interface;
- hidden mechanisms do not change the current answer.

When this is true, stop opening layers and answer the task.

Do not turn STOP into silence, skipped conclusions, or hidden UNKNOWNs.

---

# 5. Interface Closure

A usable interface needs only the task-relevant parts of:

```text
INPUT -> FLOW -> OUTPUT
ACTOR / AUTHORITY
DEPENDENCY / CONSTRAINT
FAILURE / FALLBACK
```

Add incentive, access, state, permission, or legitimacy only when they change the task answer.

A subsystem reaches task-local causal closure when:

- required input has a source or is labeled UNKNOWN/PROPOSAL;
- the interface can transmit;
- the actor has access to information and authority;
- resources and capacity are not assumed infinite;
- output satisfies the function under the current conditions;
- relevant failure has a receiver or is labeled unresolved;
- no known material contradiction remains at this resolution.

Do not expand upstream or downstream accounting unless it changes the task answer.

Example of a valid stop:

```text
gross income -> tax/deduction -> net income -> upkeep -> saving/spending
```

Do not open deduction mechanics, payment units, reserve accounts, settlement cycles, or public accounting standards unless the task depends on them.

# 7. State Stabilization

"The state handles it" does not prove capacity, authority, resources, or success.

Use STATE_STABILIZATION or STATE_STABILIZATION_SERVICE only when:

- current canon/source confirms a matching state-capacity interface; or
- the user chooses it as a working abstraction/proposal for the current analysis.

Otherwise label it REQUIREMENT, PROPOSAL, or UNKNOWN.

Minimum activation condition:

```text
local failure / overload / shortage / disruption
-> exceeds local absorption
-> threatens an essential function
```

Small variation does not trigger state stabilization by default.

Minimum result branches:

```text
failure
-> intervention attempt
-> continuity restored
   OR controlled degradation
   OR intervention failure
```

Do not assume perfect restoration, lossless balancing, universal income protection, or automatic success.

State tools are audit categories, not canonized agencies, procedures, budgets, formulas, or capacities:

- reallocation;
- emergency procurement;
- subsidy;
- reserve capacity;
- temporary expansion or takeover;
- quota/input adjustment;
- administrative allocation;
- relocation;
- strategic stock release;
- temporary rule change.

Do not select or design a specific tool unless the task requires that choice.

Relevant costs may include resource cost, administrative burden, opportunity cost, inefficiency, political friction, institutional friction, and legitimacy cost. If the source does not establish the cost, keep it UNKNOWN.

State capacity is not infinite. Intervention may fail because of shock size, duration, simultaneous essential failures, missing information, split authority, missing resources, strong opposition, veto power, or blocked external routes.

# 8. Multi-Polar State Hook

Current AetherFire state authority is multi-polar.

Split state actors only when an internal authority conflict changes the current task conclusion.

Possible actors include parliament, executive, ministries, military, Interior, Security, Counterintelligence, judiciary, Mage Council, local government, or Facility management.

If the internal graph does not change the answer, keep "state interface" as a bounded black box.

"The state handles it" must not:

- create resources from nothing;
- bypass veto power;
- collapse multi-polar authority into one actor when conflict matters;
- move failure to a node that lacks capacity or valid intake.

# 10. Quantitative Guardrails

Do not demand or invent numbers when the project has no quantitative model.

Use quantitative conclusions only when:

1. the user asks for quantitative simulation or estimation; and
2. canon, source, or an explicit hypothetical model provides usable anchors.

If numbers are requested but anchors are missing:

- ask for the missing input only if it is decisive;
- or provide labeled scenarios/ranges with explicit assumptions;
- or answer that the quantity is unknown.

Do not turn hypothetical numbers into canon estimates. Do not fake precision.

When numbers are not needed, use qualitative levels:

- minor / moderate / severe;
- absorbable / disruptive / essential;
- first bottleneck;
- likely pressure point;
- capacity not established.

# 11. Subsystem Depth Rules

## Credits and Points

Do not infer:

```text
credit != money != budget != material
```

Use current canon for each credit or point type.

If a score records contribution and unlocks eligibility, the valid path may be:

```text
threshold met
-> proposal/privilege becomes eligible
-> authority approves
-> resource is allocated
```

Do not skip approval. Do not infer that a score directly buys physical resources unless canon says so.

## Facility

Allowed interface audit:

- function;
- service groups;
- resident relationship;
- management authority;
- funding at interface level;
- capacity;
- dependencies;
- competition/cooperation with independents;
- failure handoff.

Open balance sheets, bankruptcy law, capital structure, or accounting metrics only when they sit on the task's causal path or the user asks.

## Dorm

Allowed interface audit:

- residency conditions;
- allocation;
- capacity;
- relation to Facility or work zone;
- overload;
- maintenance;
- access rights.

Do not open the full housing economy, land market, mortgage/construction finance, or depreciation model by default.

## Forum

Allowed interface audit:

- discovery;
- matching;
- reputation;
- access;
- moderation;
- interface with market, gambling, or content;
- meaning of failure.

Do not open full algorithmic market design, ad-auction economics, or centralized quantitative modeling by default.

## Rule Zone

Allowed interface audit:

- permission;
- geography;
- capacity;
- status/rank/access relation;
- enforcement;
- temporary exception;
- interface with transport/work.

Do not open full urban land-price modeling or location economics by default.

Interface closure must not flatten ontology:

- Facility is not automatically housing;
- Forum is not automatically marketplace;
- interaction is not containment;
- multi-polar state is not one actor when internal conflict matters.

# 12. Common Task Routes

## Entertainment or Activity Design

Prioritize needs, user groups, function, experience, demand creation, interface with existing nodes, capacity/conflict, and missing participant groups.

Do not shift into public finance, banking, or monetary economics unless the task requires it.

## Facility Audit

Funding may be opened at the interface level: source category, capacity, management incentive, and failure handoff.

Open insolvency or deep finance only when that is the audit issue.

## Economy Mention

Mentions of economy, funding, market, labor, housing, trade, or supply remain interface-scoped by default.

Treat the task as full-economy work only when the user explicitly asks for a full-economy audit, macro model, or system-wide economic design.

## Market Shock

Default trace:

```text
shock
-> first-order pressure
-> local adaptation
-> overflow/failure
-> intervention threshold
-> state attempt if a valid interface exists
-> consequence
```

No macro equilibrium model is required unless it changes the task conclusion.

## Nationalization or Strategic Takeover

Check trigger, legal/political authority path, temporary vs permanent action, result branches, and relevant costs.

Open valuation, compensation, capital restructuring, or accounting only when the user asks or they change feasibility/conclusion.

## Supply Stabilization

Default trace:

```text
normal allocation
-> shortage
-> local adjustment
-> reserves/procurement/reallocation
-> state attempt if essential and valid
```

If resources do not exist, external routes are blocked, or capacity is exceeded, state stabilization cannot create supply by itself.

# 13. Real-World Reference

Real-world economics may be used only as:

- labeled comparison;
- feasibility check;
- negative test;
- mechanism analogy requested by the user;
- support for a real-world premise that the task explicitly uses.

It must not generate required structures for AetherFire by default.

Do not infer that AetherFire needs a layer merely because real economies often have it.

---

# 14. Unknowns and Proposals

An unclear mechanism is UNKNOWN, not BROKEN.

UNKNOWN can remain long-term when the current interface is sufficient.

If a missing interface must be patched, label the patch PROPOSAL and state:

- problem solved;
- assumptions used;
- abstraction level;
- canon areas affected if accepted.

A proposal must be the minimum viable interface that solves the identified gap.

Do not propose a full subsystem unless the user asks for subsystem design.

Rejected proposals do not modify existing canon.

---

# 15. Output Rules

When opening another layer, state briefly how that layer changes one of:

- conclusion;
- authority;
- feasibility;
- exploit path;
- failure path;
- canon-status label.

When interface closure is reached:

1. stop opening mechanisms;
2. answer the current task;
3. name material UNKNOWNs;
4. mention deferred layers only if they could change the conclusion or the user needs to choose the next step.

Do not dump the checklist into every answer.
